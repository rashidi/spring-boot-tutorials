When processing large relational datasets, a single-threaded chunk step quickly becomes an I/O bottleneck. Spring Batch partitioning solves this by splitting the dataset into independent, non-overlapping ranges and executing a worker step concurrently across multiple threads or nodes.

In this tutorial, we explore how to implement a partitioned step in https://spring.io/projects/spring-batch[Spring Batch 6] backed by Java 25 virtual threads and PostgreSQL, verified with https://testcontainers.com/[Testcontainers].

== Background

A partitioned step consists of a *manager step* and multiple *worker step executions*:

* *Partitioner*: Inspects the dataset bounds (such as `MIN(id)` and `MAX(id)`) and emits an `ExecutionContext` per slice.
* *PartitionHandler*: Dispatches each partition's `StepExecution` using a `TaskExecutor` (local concurrency) or messaging channel (remote workers).
* *Worker Step*: Executes `@StepScope`-bound readers, processors, and writers isolated to each partition's key range.

Because each partition maintains its own `StepExecution` in the Spring Batch `JobRepository`, failed runs can be restarted to reprocess only incomplete partitions.

== Partitioning Implementation

=== Range Partitioner

In link:{source-main}/invoice/InvoicePartitioner.java[`InvoicePartitioner`], we query the minimum and maximum pending invoice IDs via `JdbcClient` and divide the range into `gridSize` non-overlapping `ExecutionContext` entries:

[source,java]
----
@Override
public Map<String, ExecutionContext> partition(int gridSize) {
    var bounds = jdbcClient.sql("SELECT MIN(id) AS min_id, MAX(id) AS max_id FROM invoices WHERE status = 'PENDING'")
            .query((rs, rowNum) -> new IdBounds(
                    rs.getObject("min_id", Long.class),
                    rs.getObject("max_id", Long.class)))
            .single();

    if (bounds.minId() == null || bounds.maxId() == null) {
        return Map.of();
    }
    // Split [minId..maxId] into gridSize ExecutionContext slices
}
----

=== Manager & Worker Step Configuration

In link:{source-main}/invoice/InvoicePartitionJobConfiguration.java[`InvoicePartitionJobConfiguration`], the manager step dispatches worker executions across Java 25 virtual threads while each `@StepScope` `JdbcPagingItemReader` reads only its assigned `minId`–`maxId` slice:

[source,java]
----
@Bean
Step partitionStep(JobRepository jobRepository, Step workerStep, InvoicePartitioner partitioner) {
    var taskExecutor = new SimpleAsyncTaskExecutor("batch-partition-");
    taskExecutor.setVirtualThreads(true);

    return new StepBuilder("partitionStep", jobRepository)
            .partitioner("workerStep", partitioner)
            .step(workerStep)
            .gridSize(4)
            .taskExecutor(taskExecutor)
            .build();
}
----
