== Motivation

These tutorials are created with testing and best practices in mind, inspired by daily work and questions from the
community. The goal is to provide a reference for developers to learn and apply in their projects. I have chosen not to
use mock frameworks in tests, opting instead to write integration tests with actual databases and services. This is,
and always will be, my primary goal.

With the help of https://github.com/dependabot[Dependabot], each tutorial is also kept up-to-date with the latest
dependencies. Currently, we are using Java https://adoptium.net/en-GB/temurin/releases?version=25[Temurin 25]
with https://plugins.gradle.org/plugin/org.springframework.boot/4.1.2[Spring Boot 4.1.2].

== Repository Layout and Build

Tutorials live under `<category>/<topic>/`, grouped into `ai`, `batch`, `core`, `data`, `messaging`,
`modulith`, `test`, and `web`. For example, `data/jpa-audit` is Gradle project `:data:jpa-audit`,
and `modulith/core` is `:modulith:core`.

The included `build-logic` build provides `zin.rashidi.tutorial-conventions`, which configures Java 25,
Spring Boot, dependency management, Maven Central, JUnit Platform, and JaCoCo. Tutorial builds apply
this plugin and declare only their own dependencies and custom configuration.
The root settings automatically discovers `*/*/build.gradle.kts`; new tutorials need no local settings or wrapper.

With Java 25 and Docker available, run the root Gradle wrapper:

[source,bash]
----
./gradlew :data:jpa-audit:test
./gradlew :test:contract-consumer:check
./gradlew check
----

The root `check` runs all tutorial tests, generates `testCodeCoverageReport`, and enforces
80% minimum aggregate instruction coverage via `testCodeCoverageVerification`.
The aggregate HTML report is at `build/reports/jacoco/testCodeCoverageReport/html/index.html`.

=== Local Development with Sparse Checkout

Use Git sparse checkout to keep only the tutorials or categories you are working on in your local
working tree. From the repository root in an existing clone, enable cone mode and select a tutorial
alongside the Gradle wrapper support files and shared build logic:

[source,bash]
----
git sparse-checkout init --cone
git sparse-checkout set gradle build-logic data/jpa-audit
----

Cone mode also retains root files such as `gradlew`, `settings.gradle.kts`, and `build.gradle.kts`.
Keep `gradle` and `build-logic` selected so the root wrapper and convention plugin remain available.

Add another tutorial or an entire category without replacing the current selection:

[source,bash]
----
git sparse-checkout add ai/pgvector
git sparse-checkout add web
----

Because `settings.gradle.kts` dynamically discovers `*/*/build.gradle.kts`, Gradle and the IDE
automatically configure only the checked-out tutorial modules. Reload the Gradle project in your IDE
after changing the selection. Run targeted tasks from the root as usual, for example
`./gradlew :data:jpa-audit:test`; root coverage aggregation also uses only the available tutorials.

The contract consumer depends on the producer's stubs, so include both when working on it:

[source,bash]
----
git sparse-checkout add test/contract-consumer test/contract-producer
----

Restore the full working tree when you need all tutorials:

[source,bash]
----
git sparse-checkout disable
----
